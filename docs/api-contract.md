# VYRA backend API & WebSocket contract

This documents the **actual, implemented** contract in `apps/worker/src` and `packages/core/src`
as of this revision — nothing here is proposed or aspirational. Shared wire types live in
`packages/core/src/contracts.ts` and are imported by both the worker and any client.

All responses are JSON. All endpoints are under `/api/`; anything else is served as a static
asset (the mobile web build / capture app). `protocolVersion` is currently always `1`.

## Authentication

Guests authenticate with a bearer token, not a username/password:

```
Authorization: Bearer <64-char lowercase hex token>
```

The token is generated by the server on guest creation, returned once, and never stored in
plaintext — only its SHA-256 hash is kept in D1 (`profiles.token_hash`). There is no password,
email, or account recovery; losing the token means losing the profile. This is a deliberate
prototype trust boundary, not an oversight (see `docs/roadmap.md`).

Requests to real routes without a valid bearer return `401 AUTH_REQUIRED` (missing/malformed
header) or `401 INVALID_SESSION` (well-formed but unknown token). **Note:** unknown `/api/*`
routes are matched against auth *before* the final 404 fallback, so an unauthenticated request to
a nonexistent route also returns 401, not 404 — this is existing, intentional behavior (don't
reveal route existence before identity), not a bug.

## CORS

`Access-Control-Allow-Origin` is only ever set to the exact request `Origin` when that origin
appears verbatim in the `CORS_ORIGINS` env var (comma-separated) or matches the request's own
origin. There is no wildcard fallback. Requests with no `Origin` header (native app / server-to-
server) pass through without CORS headers, which is correct — CORS is a browser enforcement
mechanism only.

## REST endpoints

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/health` | none | `{ ok, protocolVersion, aiEnabled }` |
| POST | `/api/guests` | none | Create a guest profile + token |
| GET | `/api/profile` | bearer | Fetch the caller's profile |
| POST | `/api/profile/equip` | bearer | Equip an owned cosmetic |
| POST | `/api/matches` | bearer | Create a solo or pvp (room-code) match |
| POST | `/api/rooms/:code/join` | bearer | Join a pvp match by its 6-character room code |
| POST | `/api/matches/:id/ticket` | bearer | Mint a one-time ticket to connect to that match's socket |
| GET | `/api/matches/:id/ws?ticket=` | ticket (query param) | Upgrade to the match WebSocket |
| POST | `/api/matchmaking/ticket` | bearer | Mint a one-time ticket to connect to the matchmaking socket |
| GET | `/api/matchmaking/ws?ticket=` | ticket (query param) | Upgrade to the matchmaking WebSocket |

### `POST /api/guests`

Request: `{ "name": string }` (1–24 visible characters after trimming/control-char stripping).
Response `201`: `{ "token": string, "profile": Profile }`.
Errors: `400 INVALID_NAME`.

### `GET /api/profile`

Response `200`: `Profile` (see shape below). `404 PROFILE_NOT_FOUND` if the token is valid but the
row is somehow gone (should not happen in normal operation).

```ts
interface Profile {
  id: string; name: string; xp: number; activeDays: number;
  stage: 'starter' | 'developing' | 'strong' | 'elite' | 'legendary';
  streak: number; lastActiveDay: string | null; weeklyActiveDays: number;
  totalReps: number; wins: number; qualifiedMatches: number;
  ownedCosmetics: string[]; equipped: Partial<Record<CosmeticSlot, string>>;
}
```

### `POST /api/profile/equip`

Request: `{ "slot": CosmeticSlot, "itemId": string }`. Response `200`: the updated `Profile`.
Errors: `400 INVALID_COSMETIC` (unknown item/slot pair), `403 COSMETIC_LOCKED` (not yet unlocked).

### `POST /api/matches`

Request: `{ "mode": "solo" | "pvp" }`. Response `201`: `{ "matchId": string, "roomCode": string }`.
For `solo`, a bot opponent is added automatically. For `pvp`, the caller becomes the sole member
until someone joins via room code (or matchmaking pairs them — see below).
Errors: `400 INVALID_MODE`, `404 PROFILE_NOT_FOUND`, `503 ROOM_UNAVAILABLE` (room-code collision
retries exhausted — practically never happens).

### `POST /api/rooms/:code/join`

Path param: 6-character room code (case-insensitive, normalized to uppercase). Response `200`:
`{ "matchId": string, "roomCode": string }`. Joining a room you're already a member of is a safe,
idempotent no-op (returns the same match info) — this supports retrying a request that may have
already succeeded. Errors: `404 ROOM_NOT_FOUND`, `409 ROOM_UNAVAILABLE` (full or already started).

### `POST /api/matches/:id/ticket` and `/api/matchmaking/ticket`

Response `200`: `{ "ticket": string }` — a single-use, 30-second-lived credential for the *next*
WebSocket connection only. Minting a new ticket for the same match/queue invalidates any
previous unused ticket for that player. Errors: `403 MATCH_MEMBERSHIP_REQUIRED` (match ticket
only — you must be a match member before a ticket can be minted).

### `GET /api/matches/:id/ws?ticket=` and `/api/matchmaking/ws?ticket=`

Not authenticated via `Authorization` header (browsers can't set custom headers on WebSocket
upgrades) — the ticket **is** the credential, consumed exactly once on successful upgrade.
`401 INVALID_TICKET` (missing/malformed/expired/already-used), `409 ALREADY_CONNECTED` (this
player already has an open socket here), `426 WEBSOCKET_REQUIRED` (not a WS upgrade request).

## Match WebSocket protocol (`/api/matches/:id/ws`)

Client → server (`ClientCommand`):

| type | fields | meaning |
|---|---|---|
| `ready` | — | Mark the sender ready. Battle starts only once **all** pvp members are ready — the server decides this, never the client. |
| `rep` | `event: RepEvent` | Report one completed repetition |
| `tracking` | `phaseId, visible, confidence` | Report live camera coverage during the current exercise phase |
| `stop` | `reason` | End the match now; no winner, no reward |
| `ping` | `sentAt` | Heartbeat / latency probe |

Server → client (`ServerEvent`):

| type | fields | meaning |
|---|---|---|
| `snapshot` | `snapshot: MatchSnapshot` | Full authoritative state, broadcast to all members after every state change |
| `error` | `code, message` | A command was rejected (see rep rejection codes below) |
| `pong` | `sentAt, serverNow` | Reply to `ping` |

`MatchSnapshot` (the only state a client needs — it is not a delta, always the full picture):

```ts
interface MatchSnapshot {
  protocolVersion: 1; id: string; roomCode: string; mode: 'solo' | 'pvp';
  phase: 'lobby'|'countdown'|'squat'|'transition'|'pushup'|'resolve'|'recovery'|'finished'|'interrupted';
  round: number; phaseId: string; phaseStartedAt: number; phaseEndsAt: number; serverNow: number;
  players: PlayerState[]; template: 'recovery'|'balanced'|'push'; decision: GameMasterDecision;
  winnerId: string | null; reason?: string; rewards?: Record<string, RewardReceipt>;
}
```

### Match phase flow

```
lobby --(both members ready)--> countdown --> squat --> transition --> pushup --> resolve
  --(match not over)--> recovery --> squat  (next round, up to 3 rounds total)
  --(KO or round 3)--> finished
any active phase --(disconnect / heartbeat timeout)--> interrupted
lobby with both seats filled --(one side never connects, 12s)--> interrupted   [hardened — see below]
```

Timing (from `packages/core/src/catalog.ts`, not configurable per-request): countdown 5s,
transition 12s, resolve 2s, recovery 12s, exercise phase length depends on the current
`template` (`recovery`/`balanced`/`push`), max 3 rounds.

Combat, each round: squats raise the squatter's own guard (5%/rep, capped 40%); push-ups deal
`round(8 × pushups × (1 - opponent's guard))` damage. Both players' pushup totals are resolved
**simultaneously** at the end of the round — HP never changes on individual rep arrival, only at
settlement. `winnerId` is the higher-HP player, or `null` for a draw/interruption.

### Rep rejection codes (`error.code` after a `rep` command)

| code | meaning |
|---|---|
| `WRONG_PHASE` | Rep's `phaseId`/`exercise` doesn't match the current window |
| `DUPLICATE_REP` | `seq` not strictly greater than the last accepted sequence (silently ignored, not surfaced as an error to avoid noisy retries) |
| `UNVERIFIED_REP` | Confidence below 0.65, or malformed `modelVersion` |
| `LATE_REP` | Timestamp outside the exercise window / arrived too late / from the future |
| `REP_TOO_FAST` | Faster than the minimum physical interval (600ms squat / 800ms push-up) |
| `INVALID_REP` | Missing/malformed rep event |

### Reconnection

A player may reconnect (new ticket, new socket) at any point. If the match already finished and
this player's reward was already settled, the reconnecting socket receives the **same** snapshot
and receipt — settlement is idempotent and never runs twice for the same match+player (see
`rewards.ts`). There is no mid-match reconnect-to-resume: disconnecting during an active phase
interrupts the match (this is a known, deliberate limitation — see `docs/roadmap.md`).

## Matchmaking — "Battle with Randoms"

Additive only. The existing room-code flow is completely unchanged. Matchmaking's only job is to
pair two strangers and then hand them into the **same, unmodified** match engine described above.

```
1v1 Arena
├── Battle with Randoms:  ticket → matchmaking ws → [searching] → [matched] → close →
│                         (join the match exactly like the room-code path below)
└── Room code:            create/join by code
                              ↓
                    both connect to /api/matches/:id/ws
                              ↓
                    both send `ready` (server-gated, both required)
                              ↓
                    countdown → existing match engine takes over
```

### Matchmaking WebSocket protocol (`/api/matchmaking/ws`)

Client → server (`MatchmakingCommand`): `cancel` (leave the queue, close), `ping`.

Server → client (`MatchmakingEvent`):

| type | fields | meaning |
|---|---|---|
| `searching` | — | No opponent yet; waiting in queue |
| `matched` | `matchId, roomCode` | Paired. Both sockets receive this. Disconnect from this socket and proceed exactly like the room-code flow: mint a match ticket, connect to `/api/matches/:id/ws`, send `ready`. |
| `error` | `code, message` | `INVALID_COMMAND` / `UNKNOWN_COMMAND` |
| `pong` | `sentAt, serverNow` | Reply to `ping` |

There is no `ready`/`opponent_joined`/`battle_starting` event on this socket — once `matched` is
sent, everything the client needs (opponent present, ready state, countdown, phase changes) is
already carried by the existing `MatchSnapshot` broadcast on the match socket. Duplicating that
here would be a second source of truth for the same state.

### Matchmaking guarantees

- **Atomic pairing, no self-match:** the queue is a single Durable Object instance, so pairing
  decisions are made synchronously (before any `await`) — there is no window where two concurrent
  connections can both claim the same waiting opponent, and a player can never be paired with
  themselves (`packages/core/src/matchmaking.ts`, unit-tested in `matchmaking.test.ts`).
- **No duplicate queue membership:** entering while already queued is a harmless no-op; opening a
  second concurrent socket for the same player while the first is still open is rejected with
  `409 ALREADY_CONNECTED` (same pattern as the match socket).
- **Clean disconnect/cancel:** closing the socket or sending `cancel` removes the player from the
  queue immediately — a vanished searcher cannot be handed to a later stranger as a ghost match.
- **Server-authoritative battle start:** matchmaking creates the match and adds both members, but
  the battle does not start until both independently send `ready` on the match socket — this is
  the existing, unmodified `readyPlayer` gate, not new logic.
- **Known, stated limitation:** the queue is a single global instance (no sharding). Reasonable at
  current scale; a documented tradeoff, not an oversight. There is also no cross-check preventing
  a player from entering a *new* matchmaking search while a previous matched-but-never-connected
  match still exists — that stale match self-heals via the lobby-abandonment timeout below rather
  than being explicitly blocked, to avoid adding a new global "active match" index for a case this
  timeout already resolves within ~12 seconds.

## Hardening notes (this revision)

- **Lobby abandonment timeout (new):** previously, a pvp match with both seats filled but one
  side never actually connecting/pinging could sit in `lobby` forever — no alarm was ever armed
  for that phase. `lobbyAbandoned()` in `packages/core/src/match.ts` + a `schedule()` change in
  `match-room.ts` now interrupt such a match after the existing 12-second heartbeat timeout. A
  lone host still waiting for someone to use their room code is explicitly exempt (that wait is
  unbounded by design), as is solo mode.
- **HTTP layer test coverage (new):** `apps/worker/src/http.test.ts` covers `readJson` (content-
  type, malformed/array/oversized bodies, exact 8192-byte boundary), `authenticate` (missing/
  malformed/unknown token), and `corsHeaders` (allowed origin, rejected origin, no wildcard).
  Previously only exercised indirectly via the live smoke script.
- Manually verified live against a running local worker (not just unit tests): 401 vs 404 auth-
  before-routing order, CORS header presence/absence for allowed/disallowed origins, ticket
  invalidation on re-mint, idempotent duplicate room-join, exact request-body size boundary.

## What the AI Game Master can and cannot affect

`chooseNextRound` (`apps/worker/src/game-master.ts`) picks one of exactly three fixed templates
(`recovery`/`balanced`/`push`, affecting only exercise duration) plus a short display reason. It
cannot change damage, HP, exercises, or rewards — those are pure functions in `match.ts`
independent of the AI's output. Disabled (`AI_ENABLED=false`, the shipped default), no camera
tracking coverage, a 2.5-second timeout, a malformed/unsupported response, or a thrown error all
fall back identically to `{ template: 'balanced', source: 'fallback' }`. The match is fully
playable with `AI_ENABLED=false` forever — this is the default, tested configuration.

## Deployment configuration boundary

See `docs/deployment.md` for the full walkthrough. In short: `apps/worker/wrangler.jsonc` ships
with a placeholder D1 `database_id` and localhost-only `CORS_ORIGINS` (now explicitly commented
as **required to change** before a real deploy). No Cloudflare account is authenticated in this
environment, so no deploy has been attempted or claimed — `wrangler deploy --dry-run` (bundle-only,
no cloud resources touched) passes with the current binding set including `Matchmaking`.
